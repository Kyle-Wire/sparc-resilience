## Design decisions

- **Sequential path unchanged**: `_use_ddp` is `False` by default (requires explicit opt-in via `ddp_enabled: true` in config + multi-GPU machine). No behaviour change for existing single-GPU runs.
- **Shared state dict (`_fold_shared`)**: 76 items covering all arch hyperparams, training params, JEPA config, EWC/OT config, device flags. Avoids closure capture so the fold body is spawn-safe.
- **Tensor sharing in DDP path**: tensors moved to CPU + `share_memory_()` before `spawn`; each worker calls `.to(device)` inside `_ddp_fold_worker`. The sequential path is a no-op check (tensors already on device).
- **`ss` naming**: avoids collision with `for s in surrogates.values()` loop variable inside `_exec_cv_fold`.

## Implementation Note — BF-1: Windows CP437/CP1252 encoding fix for Stage 0 summary lines
- Files changed: sparc/run/console.py
- What was done: Added `UnicodeEncodeError` fallback in `_VerbosityFilter._emit()`. When the downstream stream (Windows CP437/CP1252 pipe) cannot encode Unicode math symbols (κ U+03BA, ν U+03BD, ε₀ U+03B5+U+2080), the line is re-encoded with `errors='replace'` (κ→?) and written rather than silently dropped. Root cause was a double-cascade: (1) in DEBUG mode, `print(f"...ε₀=...")` in `nuts.py` raised UnicodeEncodeError propagating from within NUTS sampling, causing fit_matern to report "NUTS failed"; (2) in NORMAL mode, the filter's `_downstream.write("...κ=...")` raised UnicodeEncodeError caught by bare `except Exception: pass` → line silently disappeared. Also reverted an earlier `reconfigure(encoding='utf-8')` attempt that caused double-encoding in PowerShell Tee-Object pipes (UTF-8 bytes misread as CP437, then re-encoded as UTF-8 → garbled é→├⌐). 
- Tests: 4/4 test_stage0_migration.py pass; 11/11 render tests pass; manual smoke: Stage 0 produces per-variable Matérn fit and anisotropy lines for all 7 variables.
- What was learned: Windows PowerShell's Tee-Object reads Python's pipe output using the OEM/CP437 code page. Reconfiguring Python's stdout to UTF-8 before installing the filter causes double-encoding: Python emits UTF-8 bytes, but PowerShell reads them as CP437 characters, then Tee-Object writes the "decoded" string as CP437 or UTF-8 again — producing garbage. The correct fix is to keep the system encoding but specifically catch `UnicodeEncodeError` and retry with `errors='replace'`. The line appears with ASCII-safe `?` placeholders but is readable and visible.

## Implementation Note — BF-2: ASCII transliteration of Unicode math symbols in Stage 0 print statements
- Files changed: sparc/run/correlogram_analysis.py, sparc/run/anisotropy.py
- What was done: Replaced all non-ASCII characters in terminal-facing print calls. In `correlogram_analysis.py`: `Matérn`→`Matern`, `κ`→`kappa`, `ν`→`nu` in both the success and warning print lines. In `anisotropy.py` `_theta_to_compass`: `–` (EN DASH U+2013)→`-`; in `_make_dominant_direction_hint`: `±`→`+/-`, `°`→`deg`. Root cause confirmed: PowerShell `2>&1` decodes subprocess stdout bytes using the OEM code page (CP437 on this machine), so CP1252 `\xe9` (é) is decoded as Θ (CP437 `\xe9`=U+0398) then re-encoded as UTF-8 `\xce\x98`. Similarly `\xb1`(±)→▒, `\xb0`(°)→░, `\x96`(–)→û. The BF-1 `errors='replace'` fallback was already preventing silent drops; BF-2 eliminates the source of the encoding noise entirely.
- Tests: 4/4 test_stage0_migration.py + 11/11 render tests = 15/15 pass.
- What was learned: PowerShell 5.1's `2>&1` re-encoding is the correct explanation for the Θ/▒/░/û artifacts: confirmed by direct byte-level test — `sys.stdout.buffer.write(b'\xe9')` without 2>&1 preserves `\xe9` in file, but with `2>&1` produces `\xce\x98` (UTF-8 Θ) in file. The fix to use ASCII is simpler and more robust than trying to reconfigure stdout encoding, which has cascading side-effects in PowerShell pipes.
