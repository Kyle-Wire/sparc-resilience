## Grounded Directions

### Direction 1 — Epoch-Level tqdm Bar in `_exec_cv_fold`

**Gap:** `sparc/run/v2_neural_training.py` line 866: `for epoch in range(n_epochs)` — a tight loop running 60–200+ iterations with no TTY feedback. The only output is `logger.info(...)` which requires `logging.basicConfig(level=logging.INFO)` to appear — invisible during a default `sparc run`. For a typical city (N≈3000, 100 epochs, 3 folds), this is the longest user-wait in the pipeline with no feedback at all.

**Roadmap reference:** Phase 1.5 (validation runs require the user to watch and interpret training) + general UX quality for all phases.

**Academic method:** Standard tqdm pattern for training loops (Howard & Gugger 2020, *fastai* library; Zaharia et al. 2018, *MLflow* progress concepts). Key technique: wrap `range(n_epochs)` with `tqdm(..., leave=False, unit="ep")` and call `bar.set_postfix(loss=..., r2=...)` at each epoch. Use `disable=not sys.stdout.isatty()` for CI safety.

**Minimal implementation:**
```python
# sparc/run/v2_neural_training.py — _exec_cv_fold, epoch loop (line ~866)
from tqdm import tqdm
_epoch_bar = tqdm(
    range(n_epochs),
    desc=f"  Fold {fold_idx+1}/{len(ss['folds'])} epochs",
    disable=not sys.stdout.isatty(),
    leave=False,
    unit="ep",
)
for epoch in _epoch_bar:
    ...
    _epoch_bar.set_postfix(loss=f"{epoch_loss:.4f}", r2=f"{_last_r2:.3f}", curriculum=_curric_stage)
```
Files touched: `sparc/run/v2_neural_training.py` (1 change, ~10 lines), `import sys` already present.

### Direction 2 — Pipeline-Level StageProgress Module

**Gap:** `sparc/__main__.py` `cmd_run` dispatches 6 stages with bare `print(f">>> Stage X:")`. No elapsed time, no overall progress count (e.g., `[2/6]`), no stage-level timing summary at the end. The user has no idea whether a stage took 3 seconds or 3 minutes.

**Roadmap reference:** Applies to all phases — this is the entry point for every SPARC user.

**Academic method:** TQDM's `tqdm_auto` + `set_description` pattern. Industry standard: every major CLI tool (pip, Black, Ruff, Poetry) shows `[N/M]` stage counting + elapsed time. The `click` library's `ProgressBar` context manager and `rich.progress.Progress` are the two canonical approaches; since we have `tqdm` already, the equivalent is a `tqdm(STAGES, ...)` outer bar.

**Minimal implementation (`sparc/run/progress.py` — new file, ~70 lines):**
```python
import sys, time
from tqdm import tqdm

STAGE_LABELS = [
    ("0",  "Correlogram Analysis"),
    ("0b", "Pipeline Configuration"),
    ("1",  "GWEN Variable Selection"),
    ("2",  "Spatial CV + Neural Training"),
    ("3",  "Causal Validation"),
    ("4",  "Scenario Simulation"),
]

class StageProgress:
    """CI-safe pipeline stage tracker. tqdm bar in TTY, timestamped prints in pipes."""
    
    def __init__(self, stage_keys: list[str]):
        self._stages = stage_keys
        self._times: dict[str, float] = {}
        self._t0 = time.perf_counter()
        self._bar: "tqdm | None" = None
        if sys.stdout.isatty():
            self._bar = tqdm(
                total=len(stage_keys), unit="stage",
                bar_format="{desc}: {bar} {n}/{total} [{elapsed}<{remaining}]",
                desc="SPARC", position=0,
            )

    def stage_start(self, key: str, label: str) -> None:
        self._times[key] = time.perf_counter()
        msg = f"[{self._elapsed():>7.1f}s] >>> {label}"
        if self._bar:
            self._bar.set_description(f"SPARC | {label}")
            tqdm.write(msg)
        else:
            print(msg)

    def stage_done(self, key: str, label: str) -> None:
        elapsed = time.perf_counter() - self._times.get(key, time.perf_counter())
        msg = f"  [{label}] done in {elapsed:.1f}s"
        if self._bar:
            self._bar.update(1)
            tqdm.write(msg)
        else:
            print(msg)

    def finish(self) -> None:
        total = time.perf_counter() - self._t0
        msg = f"\nPipeline complete — total {total:.1f}s ({total/60:.1f} min)"
        if self._bar:
            self._bar.close()
            tqdm.write(msg)
        else:
            print(msg)

    def _elapsed(self) -> float:
        return time.perf_counter() - self._t0
```
Files touched: new `sparc/run/progress.py` (~70 lines), `sparc/__main__.py` `cmd_run` (~20 line change to wrap stage dispatch).

### Direction 3 — Fold-Level Progress Bar in Neural Training Orchestrator

**Gap:** In `train_neural_meta()`, the fold loop `for fold_idx, (train_idx, test_idx) in enumerate(folds)` (line ~2650) has no tqdm bar. During DDP mode (multi-GPU) the fold bar is irrelevant, but in the default sequential path (which covers all single-GPU and CPU runs), each fold is a 2–10 minute wait with no output to the user.

**Roadmap reference:** Phase 1.1-a–1.6 all run through this loop during validation. Phase 5 leadership validation also runs repeated `sparc run` cycles.

**Academic method:** Nested tqdm (outer = folds, inner = epochs). The `position=1` kwarg in tqdm allows nested bars without screen corruption. `leave=True` on the outer bar so the fold summary persists after each fold completes.

**Minimal implementation:**
```python
# sparc/run/v2_neural_training.py — train_neural_meta, sequential fold loop (~line 2650)
fold_bar = tqdm(
    enumerate(folds), total=len(folds),
    desc="  CV Folds",
    disable=not sys.stdout.isatty(),
    unit="fold", leave=True, position=0,
)
for fold_idx, (train_idx, test_idx) in fold_bar:
    fold_bar.set_description(f"  CV Fold {fold_idx+1}/{len(folds)}")
    test_out, oof_p, oof_s = _exec_cv_fold(...)
    fold_bar.set_postfix(r2=f"{_last_fold_r2:.3f}")
```

### Direction 4 — Dataset-Tier-Aware Pre-Run ETA Estimation

**Gap:** At the start of `cmd_run`, after Stage 0 completes, the user has no idea whether Stage 2 will take 2 minutes or 45 minutes. `DatasetProfiler` already classifies datasets into `{small, medium, large, xlarge}` tiers and this profile is stored in the artifact DB after Stage 0. No ETA lookup table or pre-run time estimate is produced.

**Roadmap reference:** Phase 3 zero-shot mode will run over much larger satellite-derived datasets — ETA becomes critical.

**Academic method:** Empirical throughput calibration (similar to sklearn's `verbose` timing annotations, or PyTorch Lightning's epoch-time projection). Maintain a simple `STAGE2_ETA_SECONDS: dict[str, int]` table in `progress.py` keyed by dataset tier × hardware profile (CPU/GPU). After hardware detection and Stage 0 profiling, print: `Estimated Stage 2 time: ~8 min (medium dataset, CPU)`. This is a rough lower-bound, not a guarantee.

**Minimal implementation:**
```python
# sparc/run/progress.py — ETA table
_STAGE2_ETA = {
    # (size_tier, has_gpu) -> seconds
    ("small",  False): 90,   ("small",  True): 30,
    ("medium", False): 480,  ("medium", True): 120,
    ("large",  False): 1800, ("large",  True): 360,
    ("xlarge", False): 5400, ("xlarge", True): 900,
}

def print_eta_hint(size_tier: str, has_gpu: bool) -> None:
    est = _STAGE2_ETA.get((size_tier, has_gpu))
    if est:
        mins = est // 60
        print(f"  [ETA hint] Stage 2 estimated ~{mins} min ({size_tier} dataset, "
              f"{'GPU' if has_gpu else 'CPU'})")
```
Files touched: `sparc/run/progress.py` (~20 lines), `sparc/__main__.py` (~5 lines to call it after Stage 0).

### Direction 5 — Stage Timing Persistence to Artifact Store

**Gap:** Stage elapsed times are computed but ephemeral — they exist only in the terminal output. The artifact store (`artifacts.db`) already tracks stage completion status (via `_mark_stage_done`) but not timing. Storing timing data enables (a) learning actual ETA factors per machine, (b) surfacing timing summaries in the desktop app, (c) diagnosing performance regressions.

**Roadmap reference:** Phase 2 (central registry) will want per-city pipeline timing metrics for registry health monitoring.

**Academic method:** Standard structured logging / telemetry. MLflow, W&B, and ClearML all persist step timing as metadata. The SPARC artifact store already has `write_struct()` — using it for timing is zero-new-infrastructure.

**Minimal implementation:**
```python
# In _mark_stage_done() / StageProgress.stage_done() — ~5 lines
_store.write_struct(
    stage_key, "stage_timing",
    {"stage": stage_key, "elapsed_s": elapsed, "timestamp": time.time()},
    producer="sparc.__main__",
)
```

## Blue-Sky Ideas

### Idea 1 — WebSocket Live Progress Streaming to Desktop App

**Adjacent field:** WebSockets / server-sent events (SSE) from FastAPI + React frontend state management.

**Connection to SPARC:** The desktop app (`sparc-desktop/`) already communicates with the SPARC server (`sparc/server/`). During a `sparc run` invoked from the desktop, the user sees no pipeline feedback — just a spinner. The server could emit pipeline progress events over a WebSocket endpoint (`/ws/pipeline/progress`) that the React frontend subscribes to, displaying a live stage progress bar identical to the CLI one.

**Potential payoff:** Unified progress tracking between CLI and desktop. The desktop app becomes a first-class run monitor. Users can close and reconnect without losing progress state (state stored in the artifact DB).

**Existing infrastructure:** `sparc/server/` FastAPI app exists; the artifact store's `write_struct` pattern already provides a natural event source. The desktop app is Tauri + React — websocket client is trivial to add.

**Implementation sketch:**
- Add `POST /v1/run/progress` endpoint that accepts stage progress events and broadcasts via WebSocket
- In `StageProgress.stage_start/done`, optionally call `push_progress_event()` that POSTs to the local server if `SPARC_SERVER_URL` env var is set
- Desktop subscribes to `ws://localhost:8008/ws/pipeline/progress` and renders a `ProgressBar` component

### Idea 2 — FLOP-Calibrated ETA from Torch Profiler

**Adjacent field:** Hardware-aware profiling (torch.profiler, NVML) × adaptive scheduling (Bayesian optimization over empirical throughput curves).

**Connection to SPARC:** The current ETA approach (Direction 4) uses a static lookup table by dataset tier. A better approach: run the first epoch with `torch.profiler`, measure actual FLOP/s, and project remaining epochs using `(total_FLOPs - completed_FLOPs) / measured_throughput`. This is what JAX/XLA does with its cost model and what PyTorch Lightning does with its `EpochTime` callback.

**Potential payoff:** ETA that adapts to the actual hardware (laptop CPU vs. server GPU vs. MPS) and dataset density, accurate to ±10% after the first epoch. No static lookup table needed.

**Existing infrastructure:** `sparc/config/hardware_profile.py` already detects GPU/CPU/MPS and RAM. `_time.perf_counter()` timing is already per-epoch in `_exec_cv_fold`. Adding a throughput EMA (`ema_rate = 0.8 * ema_rate + 0.2 * (1.0 / epoch_duration)`) to the tqdm epoch bar produces a dynamically-updated ETA with minimal overhead.

**Implementation sketch:**
```python
# In _exec_cv_fold epoch loop — after epoch timing:
ema_epoch_s = ema_epoch_s * 0.7 + epoch_duration * 0.3  # EWM
remaining_s = ema_epoch_s * (n_epochs - epoch - 1)
_epoch_bar.set_postfix(loss=f"{epoch_loss:.4f}", eta=f"{remaining_s/60:.1f}m")
```
This is 3 extra lines in the existing timing block — near-zero cost for significantly richer user feedback.
