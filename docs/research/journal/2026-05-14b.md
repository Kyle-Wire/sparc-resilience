## Critical Bug Found: `handleApplyAll` Calls the Wrong Endpoint

The "Preprocessed Data" pathway on the Processing page shows eight step cards:

1. Ingest CSV
2. Reproject CRS
3. Deduplicate coords
4. Impute missing values
5. Derive features
6. Standardize (z-score)
7. Spatial block split
8. Write cached arrow

When the user clicks **Apply All**, `handleApplyAll()` fires this call:

```ts
// ProcessingPage.tsx — handleApplyAll
await prepareData({ raster_paths: [] });
```

`prepareData` in `api.ts` maps to `POST /data/prepare`. That endpoint is the **Spatial Data Builder** — it runs fishnet creation and zonal stats extraction. Calling it with `raster_paths: []` silently does nothing useful. The step cards are all marked done immediately in the UI via `setSteps(steps.map(s => ({ ...s, done: true })))` — no actual CSV transformation ever occurs.

### Root Cause

There is no `/data/preprocess` endpoint. The function that **should** back this pathway exists in Python:

```python
# sparc/data/data_utils.py, line 306
def prepare_data(df: pd.DataFrame, config: dict) -> pd.DataFrame:
    ...
```

But `prepare_data` has no API endpoint and is never called from the server. The frontend UI is decorated scaffolding.

## Grounded Directions

### Direction 1 — Add `/data/preprocess` endpoint and wire to `prepare_data`

**Gap addressed:** G1, G2

The `prepare_data(df, config)` function in `sparc/data/data_utils.py` is the natural backend for the 8-step pipeline. A new `POST /data/preprocess` endpoint should:

1. Load the currently uploaded dataframe from the artifact store (same pattern as other `/data/*` endpoints).
2. Call `prepare_data(df, project_config)`.
3. Persist the result as a new data version via `versioning.save_version()`.
4. Stream Server-Sent Events so each of the 8 steps reports progress in real time.

The SSE approach matches the existing streaming pattern already used in `POST /run` and `POST /train`.

**Frontend change:** `handleApplyAll` must call a new `preprocessData()` API function that hits `/data/preprocess` and consumes the SSE stream, toggling each step's `done` flag as its corresponding event arrives.

**Implementation sketch (backend):**

```python
@app.post("/data/preprocess")
async def preprocess_data(request: Request):
    project_dir = _active_project()
    df = _load_current_dataframe(project_dir)
    config = _load_project_config(project_dir)

    async def event_stream():
        steps = [
            ("ingest",      lambda d: d),           # already loaded
            ("reproject",   reproject_crs),
            ("dedup",       deduplicate_coords),
            ("impute",      impute_missing),
            ("features",    derive_features),
            ("standardize", welford_standardize),   # ← uses welford.py
            ("spatial_split", spatial_block_split),
            ("cache_arrow", write_arrow_cache),
        ]
        for name, fn in steps:
            df = fn(df, config)  # type: ignore
            yield f"data: {{\"step\": \"{name}\", \"done\": true}}\n\n"

    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**Frontend sketch:**

```ts
// api.ts
export async function preprocessData(onStep: (step: string) => void) {
  const es = new EventSource(`${BASE}/data/preprocess`);
  es.onmessage = (e) => {
    const { step } = JSON.parse(e.data);
    onStep(step);
  };
}
```

**Success criterion:** User clicks Apply All → each of the 8 step cards lights up sequentially in the UI as the backend completes each transformation → the final processed dataframe is persisted as a new version.

### Direction 2 — Surface `/data/validate` on the Processing page

**Gap addressed:** G3

`sparc/data/validation.py::validate_dataset()` returns a structured result with three severity tiers:
- `critical` — issues that will break the pipeline (e.g., missing target column, >50% NaN)
- `warning` — issues that will degrade accuracy (e.g., high collinearity, zero-variance columns)
- `info` — suggestions (e.g., recommended coordinate projection)

The endpoint `POST /data/validate` is wired and functional. No button on ProcessingPage calls it.

**Proposed UX:** Add a **Validate** button in the toolbar alongside the existing "Apply All" and "Revert" buttons. Clicking it calls `POST /data/validate` and opens a collapsible issue panel beneath the step cards. Critical issues are shown in red with a block icon; warnings in amber; info in blue. The "Apply All" button should be disabled (with tooltip "Fix critical issues first") if any critical issues exist.

This is the single highest-leverage UX improvement: it gives the user actionable feedback before wasting compute on a broken run.

**Implementation sketch (frontend):**

```tsx
const [validationResult, setValidationResult] = useState<ValidationResult | null>(null);

const handleValidate = async () => {
  const result = await validateData();
  setValidationResult(result);
};

const hasCritical = validationResult?.critical?.length > 0;

<Button onClick={handleValidate}>Validate</Button>
<Button onClick={handleApplyAll} disabled={hasCritical}>Apply All</Button>

{validationResult && (
  <IssuePanel issues={validationResult} />
)}
```

**Success criterion:** User clicks Validate → structured issues appear within ~1 s → critical issues block Apply All with a clear reason.

### Direction 3 — Wire Welford scaler into the "Standardize" step

**Gap addressed:** G4

`sparc/data/welford.py` implements an online Welford scaler. It is not imported or used anywhere in the server. The "Standardize (z-score)" step currently does nothing.

The scaler's online design is particularly important for SPARC because:
- It supports the continual-learning use case (new cities can be normalized without re-scanning all historical data).
- The running `mean_` / `var_` state can be persisted per-project and reused at inference time for consistent normalization.

**Integration point:** Inside the new `/data/preprocess` step 6 (`standardize`), call `WelfordScaler.fit_transform(df[numeric_cols])` and serialize the fitted scaler state to the project artifact store. At inference time, `POST /run` loads the scaler state and applies `transform()` to new input batches.

**Success criterion:** After Apply All, `project_dir/artifacts/welford_scaler.pkl` exists and contains valid `mean_` / `var_` / `n_samples_seen_` fields. Running a second Apply All on the same data produces identical z-scores.

### Direction 4 — Full version picker in the UI

**Gap addressed:** G6

`GET /data/versions` returns a list of all saved dataframe versions. `POST /data/select_version` restores any arbitrary version by ID. The current UI shows only a single **Revert to Original** button that always restores version 0.

**Proposed UX:** Replace the "Revert to Original" button with a **Versions** dropdown that lists all saved versions with their timestamp and step label. Selecting a version calls `selectDataVersion({ version_id })`. A badge on the step cards shows which version is currently active.

This is important for iterative experimentation — a user may want to compare the effect of imputation strategy A vs B without re-running all 8 steps from scratch.

**Success criterion:** After 3 Apply All runs, the Versions dropdown shows 3 entries. Selecting entry 1 restores that exact dataframe and re-renders the data summary canvas.

### Direction 5 — Arrow cache write endpoint

**Gap addressed:** G5

Step 8 "Write cached arrow" has no backend. A fast Arrow/Parquet cache at the project level eliminates repeated CSV re-parsing across pipeline stages (training, inference, causal). This is the lowest-effort gap to close.

**Implementation:** Add a helper `_write_arrow_cache(df, project_dir)` that calls `df.to_parquet(project_dir / "data_cache.parquet", engine="pyarrow", index=False)`. Call it as the last step in `/data/preprocess`. The existing `/run` and `/train` stages can then load from `data_cache.parquet` when it exists (with CSV fallback).

**Success criterion:** After Apply All, `project_dir/data_cache.parquet` exists. `POST /run` log shows "loaded from parquet cache" rather than "parsed CSV".

## Novel Research Derivative Identified

### Streaming Step-Level Data Provenance for Reproducibility

**Source fields:** `ProcessingPage.tsx` preprocessing pipeline × data provenance research (Buneman et al. 2001; Halevy 2001) × MLflow-style experiment tracking

**Core idea:** Each of the 8 preprocessing steps transforms the dataframe. If the SSE stream from `/data/preprocess` also emits a hash of the output dataframe after each step, the project artifact store can record a full transformation DAG: `raw_sha256 → after_reproject_sha256 → ... → final_sha256`. This creates a lightweight lineage record with zero user effort. A researcher can re-derive any intermediate state, verify reproducibility across machines, and detect if upstream data has changed (hash mismatch on the raw file triggers a re-run prompt).

**Potential impact:** interpretability (full data lineage in the UI), new capability (cross-machine reproducibility verification), methodological (provenance-aware transfer learning — if two cities share the same raw hash up through step 4, their post-imputation representations are directly comparable)
**Relevant SPARC modules:** `sparc/data/data_utils.py`, `sparc/data/versioning.py`, `sparc/registry/store.py`, `sparc/server/app.py` (new `/data/preprocess` endpoint), `sparc-desktop/src/components/pages/ProcessingPage.tsx`
**Status:** new

## Summary

The Processing page's "Preprocessed Data" pathway is entirely non-functional today. The `handleApplyAll` handler calls the spatial builder endpoint with empty rasters — a no-op. The actual CSV transformation function (`data_utils.prepare_data`) has no API endpoint. Five backend utilities are implemented but unreachable from the UI: the validator, the Welford scaler, the versioning system (beyond revert), and the Arrow cache write. The fix requires one medium-complexity item (new `/data/preprocess` endpoint with SSE streaming + frontend wiring) and four low-complexity follow-ons. Addressing G1+G2 alone makes the entire page functional for the first time.
