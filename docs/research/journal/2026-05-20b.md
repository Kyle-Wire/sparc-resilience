### CUDA Gaps Found

**Gap CU-1 — `HardwareProfile` has no GPU fields; `force_cpu` wrongly tied to RAM tier**

`hardware_profile.py` line 100: `force_cpu=True` is hardcoded for the "low" RAM tier (< 12 GB). A user with 8 GB RAM but an RTX 3070 (8 GB VRAM) will always train on CPU. The profile has no `gpu_available`, `gpu_vram_gb`, or `gpu_name` fields. `/api/hardware` returns `force_cpu` but no GPU info — the desktop cannot show GPU status or make GPU-aware batch size recommendations.

**Gap CU-2 — No Automatic Mixed Precision (AMP)**

No `torch.cuda.amp.autocast()` or `GradScaler` anywhere in the training loops (`v2_neural_training.py` lines 1854–2200, 2700–2960). All arithmetic is FP32 on CUDA. On modern NVIDIA hardware (RTX 3080+, A100), AMP FP16/BF16 gives 2–4× speedup on the matrix multiplications in SIREN, spatial attention, and fusion layers. `torch.compile` is already applied, but AMP stacks on top for additional gain.

**Gap CU-3 — Batch size is CPU-RAM-tuned, not GPU-VRAM-tuned**

Default `batch_size = 2048` (config); capped at 512/2048/4096 by `HardwareProfile.batch_size` (which was sized for RAM, not VRAM). `spatial_minibatch_sampler` in `optimizer.py` L279–284 clamps to `_profile.batch_size`. On an RTX 3090 with 24 GB VRAM, batch 16384–32768 would fully saturate SM occupancy; SPARC uses batch 4096 (high RAM tier). The GPU sits at ~25% utilization because batches are too small.

**Gap CU-4 — GPU→CPU round-trip every epoch in the training loop**

`v2_neural_training.py` L1873: `spatial_minibatch_sampler(coords[train_idx], fold_cardinal.cpu().numpy(), ...)` — the `.cpu().numpy()` forces a GPU→CPU synchronization point every epoch. `fold_cardinal` is a `(N_train, 4)` LongTensor that lives on GPU. This sync is the bottleneck for small N datasets on fast GPUs (where compute is <1 ms but the sync is ~0.5 ms).

**Gap CU-5 — No `torch.cuda.empty_cache()` between folds**

Each CV fold allocates new model objects with `.to(device)`. At fold end, `del model, surrogates, process_net` releases Python references but CUDA's caching allocator retains the memory blocks. On low-VRAM GPUs (4–8 GB), by fold 4–5 the allocator is fragmented and may OOM even though logical usage is within bounds. The fix is one line: `torch.cuda.empty_cache()` at the end of each fold and before full retrain.

**Gap CU-6 — AMP interaction with sparse Laplacian ops (dependency)**

`sparc_joint_loss` calls `torch.sparse.mm(sparse_L, T_pred)` (the precomputed sparse Laplacian, Term E-Perf-B). PyTorch's CUDA autocast does not natively support sparse COO tensors in FP16 in all versions. Enabling AMP without guarding this call will throw `RuntimeError: expected scalar type Float but found Half`. Required: wrap sparse mm calls with `torch.autocast(enabled=False)` or convert to CSR sparse format (`sparse_L.to_sparse_csr()`), which is supported in AMP from PyTorch 2.1+.

## Grounded Directions

### Direction CU-1 — Add GPU fields to `HardwareProfile` + fix `force_cpu` logic

**Gap:** `HardwareProfile` is purely RAM-aware. `force_cpu=True` for < 12 GB RAM ignores GPU presence. No GPU metadata is available to the server or desktop.

**Roadmap reference:** Implicit in the hardware profile's role as a performance orchestrator (SPARC_Integration_Status.md "Performance" section; SPARC_Future_Roadmap.md Phase 5 "CUDA training").

**Academic method / prior art:** Standard ML framework device resolution (PyTorch Lightning `DeviceStats`, Hugging Face Accelerate `AcceleratorState`). The pattern: detect CUDA first, then RAM, and only fall back to CPU if _both_ GPU is absent AND RAM < threshold.

**Implementation sketch:**

```python
# hardware_profile.py

import torch

@dataclass(frozen=True)
class HardwareProfile:
    ...
    gpu_available: bool = False
    gpu_count: int = 0
    gpu_vram_gb: float = 0.0
    gpu_name: str = ""

def _detect_gpu() -> tuple[bool, int, float, str]:
    """Return (available, count, vram_gb, name) for best CUDA device."""
    try:
        import torch
        if not torch.cuda.is_available():
            return False, 0, 0.0, ""
        n = torch.cuda.device_count()
        props = torch.cuda.get_device_properties(0)  # primary device
        vram = props.total_memory / (1024**3)
        return True, n, round(vram, 1), props.name
    except Exception:
        return False, 0, 0.0, ""

def _build_profile(tier, total_ram_gb, available_ram_gb) -> HardwareProfile:
    gpu_avail, gpu_count, gpu_vram, gpu_name = _detect_gpu()
    ...
    if tier == "low":
        return HardwareProfile(
            ...
            # KEY FIX: force_cpu only when GPU is also absent
            force_cpu=not gpu_avail,
            gpu_available=gpu_avail,
            gpu_count=gpu_count,
            gpu_vram_gb=gpu_vram,
            gpu_name=gpu_name,
        )
```

**Files:** `sparc/config/hardware_profile.py` (~40 lines); `sparc/server/app.py` (the `/api/hardware` response already returns `effective.as_dict()` — GPU fields appear automatically once added to the dataclass).

**Success criterion:** On a machine with 8 GB RAM + RTX 3070: `detect_profile().force_cpu == False`; `/api/hardware` returns `{"gpu_available": true, "gpu_vram_gb": 8.0, ...}`; desktop shows "GPU: RTX 3070 (8.0 GB)" badge.

### Direction CU-2 — Automatic Mixed Precision (AMP) training

**Gap:** All forward/backward passes are FP32 on CUDA. On NVIDIA Ampere/Hopper hardware, FP16/BF16 Tensor Core operations run 2–8× faster than FP32 for the matrix sizes in SIREN, spatial attention, and fusion layers. The sparse Laplacian must be guarded (Gap CU-6).

**Roadmap reference:** SPARC_Future_Roadmap.md Phase 5 "CUDA training acceleration"; SPARC_Integration_Status.md notes `torch.compile` as wired but AMP as absent.

**Academic method:** NVIDIA Apex AMP → PyTorch native AMP (Micikevicius et al. 2018 *Mixed Precision Training*). BF16 is preferred over FP16 for training stability: wider dynamic range (~FP32), no overflow risk, supported by all Ampere+ GPUs and MPS.

**Implementation sketch (innermost training loop):**

```python
# v2_neural_training.py — inside CV fold training loop

_use_amp = torch.cuda.is_available() and hasattr(torch.cuda.amp, "autocast")
_scaler = torch.cuda.amp.GradScaler(enabled=_use_amp)

# In the batch loop:
with torch.autocast(device_type="cuda", dtype=torch.bfloat16, enabled=_use_amp):
    surrogate_preds, surrogate_std = _forward_surrogates(...)
    base_input = torch.stack(surrogate_preds, dim=1)
    alpha = process_net(pr_input)
    T_pred, exceedance, _ = model(...)
    
    # CRITICAL: sparse Laplacian must stay FP32
    with torch.autocast(device_type="cuda", enabled=False):
        total_loss, components = sparc_joint_loss(
            ...,
            sparse_laplacian=tensors.get("sparse_laplacian"),
        )
    
    # EWC + OT penalties (FP32-safe, guard sparse ops inside)
    if _ewc_active:
        total_loss = total_loss + _ewc_lambda * _ewc_penalty(...)

optimizer.zero_grad()
_scaler.scale(total_loss).backward()
_scaler.unscale_(optimizer)
torch.nn.utils.clip_grad_norm_(all_params, clip_norm)
_scaler.step(optimizer)
_scaler.update()
```

**Note on sparse Laplacian (Gap CU-6):** The sparse COO Laplacian must be kept in FP32. The `autocast(enabled=False)` guard on the `sparc_joint_loss` call keeps all 11 PDE terms in FP32 while the rest of the forward pass uses BF16. The performance-critical paths (SIREN, attention, fusion) are in the AMP region. The sparse matmul, though excluded, runs fast anyway (single sparse.mm on full N).

**Files:**
- `sparc/run/v2_neural_training.py` — add `_use_amp` + `_scaler` at line ~1234; wrap batch loop at ~1884; replace `total_loss.backward()` with `_scaler.scale(...).backward()` at L2131
- Apply same pattern to full-retrain loop (~L2700) and SWA loop (~L2900)
- `sparc/training/optimizer.py::training_step` — add optional `scaler` param

**Success criterion:** On CUDA machine: training log shows `AMP active (bfloat16)`; epoch wall-clock drops by ≥ 40% on a 3000-point test city; `oof_predictions` within 0.5% R² of FP32 run (same seed); no `RuntimeError: expected scalar type Float but found Half`.

### Direction CU-3 — GPU-VRAM-aware batch size in `HardwareProfile`

**Gap:** `HardwareProfile.batch_size` (512/2048/4096) was tuned for CPU RAM. On a 24 GB VRAM GPU, batch 4096 leaves the GPU at ~20–30% SM occupancy. Optimal GPU batch is `min(N, floor(gpu_vram_gb * 256))` (heuristic: 256 rows per GB VRAM for the SPARC model's ~12 KB per row footprint).

**Roadmap reference:** Hardware profile orchestration (same as CU-1).

**Academic method:** Standard ML batch scaling guidelines — linear scaling rule (Goyal et al. 2017 *Accurate, Large Minibatch SGD*). Caveat: SPARC's spatial minibatch constraint means batch must be geographically contiguous, so very large batches (> N/2) are impractical.

**Implementation sketch:**

```python
# hardware_profile.py
def _gpu_batch_size(gpu_vram_gb: float) -> int:
    """Heuristic: 256 rows per GB VRAM, clamped to [512, 32768]."""
    return int(min(max(int(gpu_vram_gb * 256), 512), 32768))

# In _build_profile():
if gpu_avail and not force_cpu:
    gpu_bs = _gpu_batch_size(gpu_vram)
else:
    gpu_bs = batch_size  # CPU fallback

# Add gpu_batch_size field to HardwareProfile
```

```python
# v2_neural_training.py — in train_neural_meta()
from sparc.config.hardware_profile import detect_profile
_hp = detect_profile()
if device.type == "cuda" and hasattr(_hp, "gpu_batch_size"):
    batch_size = max(batch_size, _hp.gpu_batch_size)
    logger.info("GPU batch size override: %d (VRAM=%.1f GB)", batch_size, _hp.gpu_vram_gb)
```

**Files:** `sparc/config/hardware_profile.py` (~10 lines); `sparc/run/v2_neural_training.py` (~5 lines)

**Success criterion:** On RTX 3090 (24 GB): `_hp.gpu_batch_size == 6144`; training log shows "GPU batch size override: 6144"; GPU utilization in `nvtop` or `watch -n1 nvidia-smi` shows ≥ 60% SM occupancy (vs ~25% before).

### Direction CU-4 — Fix `fold_cardinal.cpu().numpy()` GPU→CPU sync in training loop

**Gap:** `v2_neural_training.py` L1873: `spatial_minibatch_sampler(coords[train_idx], fold_cardinal.cpu().numpy(), ...)`. This call synchronizes GPU→CPU every epoch. `fold_cardinal` is an `(N_train, 4)` LongTensor on GPU. The fix is to keep a CPU copy from the start.

**Roadmap reference:** Performance (implicit — removes the last CPU sync in the hot loop).

**Academic method:** PyTorch best practices — keep index/structural tensors on CPU for batch construction; only push batch data to GPU. This is the standard "CPU for indices, GPU for values" pattern.

**Implementation sketch:**

In `_prepare_tensors()`, return BOTH a device tensor AND a CPU numpy array:

```python
# _prepare_tensors() — add to return dict
"cardinal_idx": cardinal_idx,           # on device (for PDE loss)
"cardinal_idx_cpu": cardinal_np,        # CPU numpy (for batch sampler)
```

Then in the fold setup:
```python
# L~1846 — use the CPU cardinal directly:
fold_cardinal_np = tensors["cardinal_idx_cpu"][train_idx]  # already numpy
batches = list(spatial_minibatch_sampler(
    coords[train_idx],
    fold_cardinal_np,            # no .cpu().numpy() needed
    batch_size=batch_size,
    n_batches=...
))
```

The `fold_cardinal` tensor on device is still needed for `_remap_indices_to_local` — that's fine. Only the sampler needs the CPU array.

**Files:** `sparc/run/v2_neural_training.py` — `_prepare_tensors()` return dict (~2 lines); fold training setup ~L1846 (~3 lines)

**Success criterion:** `torch.cuda.synchronize()` profile shows zero `cudaMemcpy(DeviceToHost)` calls during the epoch loop; training throughput improves by ~5% on a GPU with fast compute (RTX 3090+).

### Direction CU-5 — `torch.cuda.empty_cache()` between CV folds

**Gap:** Fold models are deleted but CUDA memory fragments. On 4–8 GB VRAM GPUs, later folds or the full retrain can OOM even though instantaneous usage is within bounds. Single-line fix, zero functional impact.

**Roadmap reference:** Reliability (implicit — prevents OOM failures on consumer GPUs).

**Implementation sketch:**

```python
# v2_neural_training.py — at end of each fold (after oof prediction block, ~L2250):
del model, surrogates, process_net, source_net
if torch.cuda.is_available():
    torch.cuda.empty_cache()

# And before full retrain (~L2284):
if torch.cuda.is_available():
    torch.cuda.empty_cache()
logger.info("Full retrain: CUDA cache cleared")
```

**Files:** `sparc/run/v2_neural_training.py` — ~4 lines in 2 places

**Success criterion:** On 8 GB VRAM GPU with 5 CV folds: no CUDA OOM error; `torch.cuda.memory_reserved()` returns to baseline after each fold delete + empty_cache call.

## Blue-Sky Ideas

### CUDA Graph Capture for the Epoch Step

**Source field:** CUDA Graphs (NVIDIA 2020; PyTorch `torch.cuda.CUDAGraph`) × `torch.compile` (already applied)

**Core idea:** Once `torch.compile` has traced the computation graph, CUDA Graphs can capture the entire epoch step (forward + backward + optimizer step) as a single replay-able GPU kernel sequence. The captured graph eliminates ~50 CUDA kernel launch overheads per batch step. For SPARC's batch sizes (2048–8192), kernel launch overhead is ~15–30% of compute time. `torch.cuda.make_graphed_callables([model, process_net] + surrogates)` is the modern API; it handles the "first step is not graphed" pattern automatically.

**Potential impact:** performance (15–30% additional throughput on top of AMP + torch.compile on A100/H100; effectively free throughput), zero functional change

**SPARC infrastructure to build on:** `_maybe_compile()` already exists; CUDA graph capture is a follow-on step after compile. The spatial minibatch sampler produces fixed-size batches (after the full-batch fallback for N ≤ batch_size) which are a prerequisite for graph capture (static shapes required).

**Caveat:** CUDA Graphs require static input shapes. The variable-length batch from `spatial_minibatch_sampler` means the last batch (typically smaller) needs special handling (pad to batch_size with a mask, or skip graphing for it).

---

### Multi-GPU Data Parallel Training via `DistributedDataParallel`

**Source field:** PyTorch `DistributedDataParallel` (DDP) × spatial CV fold design

**Core idea:** Each CV fold is fully independent. DDP wrapping and running fold `i` on GPU `i` would give K× speedup for K-fold CV with K GPUs. The current architecture is perfectly suited — each fold's model + surrogates fit in a single GPU's memory, and there is no cross-fold communication needed during training (only OOF collection after). `torch.multiprocessing.spawn` + DDP init + one GPU per process already patterns used by PyTorch Lightning. For the full retrain, standard DDP with `batch_size * world_size` LR scaling.

**Potential impact:** K× training speedup for K-GPU machines (K=2 → 2× for free); enables running 10-fold CV in the same wall-clock time as 1-fold CV

**SPARC infrastructure to build on:** `_maybe_compile()`, the existing fold loop in `train_neural_meta()`, the hardware profile's `gpu_count` (once Gap CU-1 is added)

**Caveat:** The spatial minibatch sampler needs a partitioned-N version for DDP (each rank processes a disjoint spatial partition). The `EWC` and `OT alignment` continual learning penalties need gradient reduction across ranks. Medium-high complexity.

### Self-Grill — Question 4

Each D2H transfer of a (3000, 4) int64 tensor is ~96 KB — negligible latency (~0.01 ms per call). The claimed "bottleneck" is overstated for typical dataset sizes.

**Revised recommendation:** The fix is still correct and clean (keep `cardinal_idx_cpu` in the tensors dict), but impact is **very low** for datasets with N < 20k. Complexity remains low (2 lines). Keep in backlog as a housekeeping item, not a performance priority.

### Self-Grill — Question 5
**What I claimed:** CU-5 (`empty_cache` between folds) is a one-line fix.
**What I found / know:** Need to find where the fold model is deleted. Looking at the fold loop structure: each fold creates `model, surrogates, process_net, source_net` inside the `for fold_idx, (train_idx, test_idx) in enumerate(folds)` loop. These are reassigned at the top of each iteration (Python garbage collects the previous fold's objects). `torch.cuda.empty_cache()` would be placed at the end of the fold loop body. Since Python GC and CUDA allocator are decoupled, the explicit call is correct.

BUT: in practice, PyTorch's caching allocator is usually smart enough to reuse freed memory blocks. The OOM risk is real but mainly affects: (a) very low VRAM (≤ 4 GB), (b) large N (> 10k) with big hidden_dim (> 512), (c) > 5 folds. For the common 4-GB case with N=3k and default hidden_dim=256, VRAM usage per fold is ~400 MB — 5 folds is well within 4 GB. The OOM scenario is edge-case.

**Revised recommendation:** `empty_cache` fix is still correct, low-complexity, and costs nothing. Appropriate to implement. But labeling it "prevents OOM on low-VRAM GPUs" is somewhat overstated — it's more accurately "reduces peak VRAM fragmentation, especially helpful for > 5 folds with large N."
**Open for user confirmation?** No.

### Self-Grill — Question 6
**What I claimed:** GPU batch size heuristic: `floor(gpu_vram_gb * 256)` rows per GB.
**What I found / know:** Need to estimate SPARC's per-row GPU memory footprint. With hidden_dim=256:
- `SPARCMetaLearner` has ~2M parameters (FP32 = 8 MB). 
- Per-row activation tensors for a batch of B: physics_feats (B × ~20), X_spatial (B × 128), knn_index (B × 128), trunk (B × 256), ... ≈ B × 600 floats ≈ B × 2.4 KB. 
- For B=2048: ~5 MB activations + 8 MB weights + gradients (~16 MB) = ~30 MB total.
- For B=8192: ~20 MB activations + 8 MB weights + gradients = ~45 MB.
- An RTX 3090 with 24 GB VRAM: safe batch ≈ 24×1024 / 45 × 8192 ≈ floor(24,000 / 45 × 8192) ≈ should be able to run B=32768 comfortably.

My heuristic `gpu_vram * 256 = 24 * 256 = 6144` is too conservative by ~5×. However: the spatial minibatch constraint (geographically contiguous blocks) typically produces batches of 300–2000 points at N=3000 (half the dataset), so even B=6144 is a ceiling that won't be hit for small cities. For large cities (N=50k), B=16384 would be appropriate. The heuristic is conservative but safe — better conservative than OOM.

**Revised recommendation:** Heuristic `gpu_vram_gb * 256` (conservative) is acceptable as a **minimum GPU batch size** (override the CPU-tuned default upward). Document as a starting point; advanced users can tune via config. Keep the implementation sketch as written.

### Self-Grill — Question 7
**What I claimed:** AMP gives 2–4× speedup for SIREN, spatial attention, and fusion.
**What I found / know:** SIREN uses `nn.Linear` + sine activation. Spatial attention uses `nn.MultiheadAttention`. Both are dominated by GEMMs which map perfectly to Tensor Cores in BF16/FP16.
